Parte 1 · Angular

Buscador de libros

Una sola pantalla: escribes en un campo y aparecen libros de Open Library. Parece simple, pero resuelve los problemas reales de cualquier buscador: no saturar la API, cancelar búsquedas viejas, mostrar "cargando" y errores.

Qué hace exactamente

  • No busca hasta que escribas al menos 3 letras.
  • Espera 300 ms después de la última tecla (no hace una petición por cada letra).
  • Si escribes algo nuevo mientras la búsqueda anterior sigue en camino, la cancela.
  • Muestra Buscando…, la cantidad de resultados, "Sin resultados" o un mensaje de error.
  • Si falla la red, el buscador sigue funcionando en la siguiente búsqueda.

Crear el proyecto#

Desde cero, con el CLI de Angular. Angular 17+ crea componentes standalone por defecto (sin NgModule).

npm install -g @angular/cli
ng new buscador --style=css --ssr=false   # responde "No" a zoneless si pregunta y no lo conoces
cd buscador
ng generate service libros/libros          # crea libros.service.ts
ng generate component libros/buscador      # crea buscador.ts / .html / .css
ng serve                                   # http://localhost:4200

Para correr el proyecto ya hecho:

cd angular-buscador
npm install
ng test --watch=false   # 5 tests en verde
ng serve

Regla prácticaAgrupa por funcionalidad (libros/, usuarios/), no por tipo de archivo (components/, services/). Así todo lo de "libros" está junto.

Componentes standalone#

Un componente es una pieza de pantalla: una clase TypeScript (lógica) + una plantilla HTML (vista) + CSS. "Standalone" significa que el componente declara él mismo lo que usa en imports, sin módulos.

@Component({
  selector: 'app-buscador',            // cómo se usa en HTML: <app-buscador />
  imports: [ReactiveFormsModule],      // lo que la plantilla necesita ([formControl])
  templateUrl: './buscador.html',
  styleUrl: './buscador.css',
  changeDetection: ChangeDetectionStrategy.OnPush,
})
export class Buscador { /* ... */ }

OnPush le dice a Angular: "vuelve a pintar este componente solo cuando cambie algo que yo uso" (un signal, un input, un evento). Con signals es la opción natural y hace la app más rápida.

El componente raíz solo coloca al buscador, y main.ts arranca todo:

// main.ts
bootstrapApplication(App, appConfig).catch((err) => console.error(err));

Signals: el estado de la pantalla#

Un signal es una caja con un valor que avisa cuando cambia. La plantilla lo lee llamándolo como función: libros(). Cuando haces .set(), Angular repinta lo que dependa de él.

readonly libros = signal<Libro[]>([]);          // estado: lista
readonly cargando = signal(false);                // estado: ¿esperando respuesta?
readonly error = signal<string | null>(null);     // estado: mensaje de error
readonly total = computed(() => this.libros().length); // derivado: se recalcula solo

this.cargando.set(true);     // escribir
this.libros();               // leer
this.total();                // leer un computed (no se puede hacer .set)
FunciónQué esCuándo usarla
signal(v)Valor que puedes cambiarEstado propio: lista, cargando, error, filtros
computed(fn)Valor calculado a partir de otros signalsTotales, listas filtradas, textos derivados
.set(v) / .update(fn)Cambiar el valorcontador.update(n => n + 1)
¿Signals o Observables?Signals para estado (lo que la pantalla muestra ahora). Observables (RxJS) para eventos en el tiempo (teclas, peticiones HTTP). Este proyecto usa los dos: RxJS procesa lo que escribes y el resultado final se guarda en signals.

Servicios e inyección de dependencias#

Un servicio es una clase para la lógica que no es de pantalla: llamar APIs, guardar datos compartidos. El componente no hace new LibrosService(); se lo pide a Angular con inject().

@Injectable({ providedIn: 'root' })   // una sola instancia para toda la app
export class LibrosService {
  private readonly http = inject(HttpClient);
}

export class Buscador {
  private readonly librosService = inject(LibrosService);
}

¿Por qué no new? Porque en los tests Angular puede darte una versión falsa (por ejemplo un HttpClient de prueba) sin tocar el componente.

HttpClient solo existe si lo registras una vez en app.config.ts:

export const appConfig: ApplicationConfig = {
  providers: [provideBrowserGlobalErrorListeners(), provideHttpClient()],
};

HttpClient y Observables#

http.get() no hace la petición en el momento: devuelve un Observable, una "receta" que se ejecuta cuando alguien se suscribe. Con .pipe() le encadenas transformaciones.

buscar(texto: string): Observable<Libro[]> {
  const params = new HttpParams().set('q', texto).set('limit', 10);
  // GET https://openlibrary.org/search.json?q=borges&limit=10
  return this.http.get<RespuestaBusqueda>(this.url, { params }).pipe(
    map((respuesta) => respuesta.docs.map(/* convertir cada doc en Libro */)),
  );
}
Usa HttpParamsEn lugar de armar la URL a mano ('?q=' + texto), HttpParams codifica espacios, tildes y símbolos por ti.

Modelo de la API vs. modelo de la app#

La API responde con nombres en inglés y campos que pueden faltar. En vez de esparcir doc.author_name?.[0] por toda la app, el servicio traduce la respuesta a un tipo propio, limpio y sin opcionales.

La API devuelve (no lo controlas)Tu app usa (lo controlas)
key: stringid: string
title: stringtitulo: string
author_name?: string[]autores: string[] (vacío si no hay)
first_publish_year?: numberanio: number | null
respuesta.docs.map((doc) => ({
  id: doc.key,
  titulo: doc.title,
  autores: doc.author_name ?? [],          // ?? = "si es null/undefined usa esto"
  anio: doc.first_publish_year ?? null,
}))

Ventaja: si mañana cambias de API, solo tocas el servicio. El componente y la plantilla no se enteran.

Formularios reactivos#

Un FormControl representa un campo. Lo interesante es valueChanges: un Observable que emite cada vez que el usuario escribe. Eso es lo que conectamos a RxJS.

readonly busqueda = new FormControl('', { nonNullable: true }); // siempre string, nunca null
<input type="search" [formControl]="busqueda" placeholder="Escribe al menos 3 letras" />

Para que [formControl] funcione, el componente importa ReactiveFormsModule.

La tubería RxJS, operador por operador#

Esta es la parte central del proyecto. Cada tecla entra por arriba y pasa por estos "filtros" en orden:

this.busqueda.valueChanges
  .pipe(
    map((texto) => texto.trim()),          // 1. quita espacios
    debounceTime(300),                      // 2. espera 300 ms de silencio
    distinctUntilChanged(),                 // 3. ignora si es igual al anterior
    filter((texto) => texto.length >= 3),   // 4. mínimo 3 letras
    tap(() => {                             // 5. efecto: mostrar "cargando"
      this.cargando.set(true);
      this.error.set(null);
    }),
    switchMap((texto) =>                    // 6. pide a la API y CANCELA la anterior
      this.librosService.buscar(texto).pipe(
        catchError(() => {                  // 7. si falla, mensaje y lista vacía
          this.error.set('No se pudo conectar. Revisa tu conexión e intenta de nuevo.');
          return of([]);
        }),
      ),
    ),
    takeUntilDestroyed(),                   // 8. se desuscribe al destruir el componente
  )
  .subscribe((libros) => {
    this.libros.set(libros);
    this.cargando.set(false);
  });
OperadorEn una fraseSin él…
mapTransforma cada valor" borges " y "borges" serían búsquedas distintas
debounceTime(300)Deja pasar el valor solo si hubo 300 ms sin teclas"borges" = 6 peticiones
distinctUntilChangedBloquea valores repetidos seguidosBorrar y reescribir la misma letra repite la búsqueda
filterDeja pasar solo lo que cumple la condiciónBuscarías con 1 letra (miles de resultados)
tapHace algo "al costado" sin cambiar el valorNo habría estado de carga
switchMapCambia a un nuevo Observable y cancela el anteriorUna respuesta vieja y lenta podría pisar a la nueva
catchErrorAtrapa el error y devuelve un valor de reemplazoUn error mataría la tubería: no volvería a buscar nunca
takeUntilDestroyedCorta la suscripción cuando el componente muereFuga de memoria
Detalle importante: dónde va catchErrorEstá dentro del switchMap, en el Observable de la petición. Si lo pones afuera, al primer error la tubería principal se completa y el buscador deja de responder. Dentro, solo "muere" esa petición y la siguiente funciona.
¿Por qué switchMap y no mergeMap?

switchMap: solo importa la última búsqueda (buscadores, autocompletar).

mergeMap: todas en paralelo (subir varios archivos).

concatMap: una detrás de otra, en orden (guardar cambios en secuencia).

exhaustMap: ignora nuevas mientras hay una en curso (botón "Pagar" con doble clic).

Plantilla: @if y @for#

Angular 17+ trae control flow integrado. Reemplaza a *ngIf y *ngFor y no necesita importar nada.

@if (cargando()) {
  <p>Buscando…</p>
} @else if (error()) {
  <p class="error" role="alert">{{ error() }}</p>
} @else if (total() > 0) {
  <ul>
    @for (libro of libros(); track libro.id) {
      <li>{{ libro.titulo }} — {{ libro.anio ?? 'Sin año' }}</li>
    }
  </ul>
}
  • track libro.id es obligatorio: le dice a Angular cómo reconocer cada elemento para no recrear toda la lista.
  • El orden de los @if define la prioridad: primero "cargando", luego "error", luego resultados.
  • role="alert" hace que los lectores de pantalla anuncien el error.

Haz el tuyo: plantilla para cualquier API#

El mismo patrón sirve para buscar países, películas, usuarios de GitHub… Solo cambian 3 cosas: la URL, el tipo de la respuesta y la conversión. Ejemplo con la API pública de países:

  1. Genera la carpeta: ng g service paises/paises y ng g component paises/buscador-paises.
  2. Define los dos modelos (API y app) y la conversión en el servicio.
  3. Copia el componente del buscador cambiando el servicio y el tipo.
// paises/pais.model.ts
export interface PaisApi {            // lo que devuelve https://restcountries.com/v3.1/name/{texto}
  cca3: string;
  name: { common: string };
  capital?: string[];
  population: number;
}

export interface Pais {               // lo que usa tu app
  id: string;
  nombre: string;
  capital: string;
  poblacion: number;
}
// paises/paises.service.ts
import { HttpClient } from '@angular/common/http';
import { Injectable, inject } from '@angular/core';
import { Observable, map } from 'rxjs';

import { Pais, PaisApi } from './pais.model';

@Injectable({ providedIn: 'root' })
export class PaisesService {
  private readonly http = inject(HttpClient);

  buscar(texto: string): Observable<Pais[]> {
    const url = `https://restcountries.com/v3.1/name/${encodeURIComponent(texto)}`;
    return this.http.get<PaisApi[]>(url).pipe(
      map((paises) =>
        paises.map((p) => ({
          id: p.cca3,
          nombre: p.name.common,
          capital: p.capital?.[0] ?? 'Sin capital',
          poblacion: p.population,
        })),
      ),
    );
  }
}
// paises/buscador-paises.ts  (misma tubería que el buscador de libros)
import { ChangeDetectionStrategy, Component, inject, signal } from '@angular/core';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import { FormControl, ReactiveFormsModule } from '@angular/forms';
import { catchError, debounceTime, distinctUntilChanged, filter, map, of, switchMap, tap } from 'rxjs';

import { Pais } from './pais.model';
import { PaisesService } from './paises.service';

@Component({
  selector: 'app-buscador-paises',
  imports: [ReactiveFormsModule],
  template: `
    <input type="search" [formControl]="busqueda" placeholder="Busca un país" />
    @if (cargando()) { <p>Buscando…</p> }
    @else if (error()) { <p role="alert">{{ error() }}</p> }
    @else {
      <ul>
        @for (pais of paises(); track pais.id) {
          <li>{{ pais.nombre }} — {{ pais.capital }}</li>
        } @empty { <li>Sin resultados</li> }
      </ul>
    }
  `,
  changeDetection: ChangeDetectionStrategy.OnPush,
})
export class BuscadorPaises {
  private readonly servicio = inject(PaisesService);

  readonly busqueda = new FormControl('', { nonNullable: true });
  readonly paises = signal<Pais[]>([]);
  readonly cargando = signal(false);
  readonly error = signal<string | null>(null);

  constructor() {
    this.busqueda.valueChanges
      .pipe(
        map((t) => t.trim()),
        debounceTime(300),
        distinctUntilChanged(),
        filter((t) => t.length >= 2),
        tap(() => {
          this.cargando.set(true);
          this.error.set(null);
        }),
        switchMap((t) =>
          this.servicio.buscar(t).pipe(
            catchError(() => {
              this.error.set('No se encontró o no hay conexión.');
              return of([]);
            }),
          ),
        ),
        takeUntilDestroyed(),
      )
      .subscribe((paises) => {
        this.paises.set(paises);
        this.cargando.set(false);
      });
  }
}

@empty es un bloque opcional de @for que se muestra cuando la lista está vacía.

Errores comunes#

NullInjectorError: No provider for HttpClient

Falta provideHttpClient() en app.config.ts (o en los providers del test).

Falta ReactiveFormsModule en los imports del componente.

Con OnPush, si guardas datos en una variable normal (this.libros = [...]) Angular no se entera. Usa un signal y .set().

El catchError está fuera del switchMap. Muévelo adentro, sobre la petición.

Error de CORS en la consola

En la plantilla sale "[object Object]" o la función entera

Olvidaste los paréntesis al leer el signal: es {{ total() }}, no {{ total }}.

Parte 1 · Angular, más allá del buscador

Headers, interceptors, guards y promesas

El buscador no los necesita, pero en cuanto tu app tiene login aparecen los cuatro: el token viaja en un header, un interceptor lo pega en cada petición, un guard impide entrar a pantallas sin sesión y, a veces, prefieres async/await en vez de Observables. Los ejemplos usan la API Flask de la Parte 2.

Headers en las peticiones#

Un header (cabecera) es un dato extra que viaja con la petición o la respuesta, con forma Nombre: valor. No es parte del cuerpo (el JSON): es la "etiqueta del sobre". Sirven para decir quién eres, qué formato mandas y qué formato aceptas.

HeaderVa en…Para qué
Content-Typepetición y respuestaFormato del cuerpo: application/json, multipart/form-data
AcceptpeticiónQué formato quieres recibir
AuthorizationpeticiónQuién eres: Bearer eyJhbGci…
Accept-LanguagepeticiónIdioma preferido (es) para mensajes del servidor
X-Request-IdambosUn id para seguir una petición en los logs (inventado, por eso X-)
X-Total-CountrespuestaTotal de resultados cuando paginas
LocationrespuestaURL del recurso recién creado (con 201)
Set-CookierespuestaEl servidor guarda una cookie en el navegador

Mandar headers en una petición

import { HttpClient, HttpHeaders } from '@angular/common/http';

// Opción 1: objeto HttpHeaders
const headers = new HttpHeaders()
  .set('Accept', 'application/json')
  .set('X-Request-Id', crypto.randomUUID());
this.http.get<LibroApi[]>(`${API_URL}/libros`, { headers });

// Opción 2: objeto simple (más corto)
this.http.get<LibroApi[]>(`${API_URL}/libros`, { headers: { 'Accept-Language': 'es' } });

// POST: HttpClient pone Content-Type: application/json solo porque el body es un objeto
this.http.post(`${API_URL}/prestamos`, { libro_id: 1, socio_id: 1 });
HttpHeaders es inmutableheaders.set(...) no cambia el objeto: devuelve uno nuevo. h.set('A', '1'); sola no hace nada; tienes que guardar el resultado: h = h.set('A', '1'). Lo mismo pasa con HttpParams y con la petición dentro de un interceptor (por eso se usa req.clone()).
Subir archivosCon FormData no pongas Content-Type a mano: el navegador lo arma con el boundary correcto. Si lo fuerzas, el servidor no puede leer el archivo.

Leer headers de la respuesta

Por defecto HttpClient te da solo el cuerpo. Con observe: 'response' recibes la respuesta completa: estado, headers y cuerpo.

this.http
  .get<LibroApi[]>(`${API_URL}/libros`, { observe: 'response' })
  .subscribe((res) => {
    const total = Number(res.headers.get('X-Total-Count'));  // header de la respuesta
    const libros = res.body ?? [];                             // el JSON
    console.log(res.status, total, libros.length);
  });

Headers + CORS: por qué a veces "desaparecen"

Cuando Angular (localhost:4200) llama a Flask (localhost:5000) con un header "no simple" como Authorization, el navegador primero manda una petición OPTIONS de prueba (preflight) para preguntar si está permitido. Y al revés: aunque Flask mande X-Total-Count, JavaScript no puede leerlo salvo que el servidor lo exponga.

En Flask se resuelve en la configuración de CORS:

CORS(
    app,
    origins=["http://localhost:4200"],
    allow_headers=["Content-Type", "Authorization", "X-Request-Id"],  # headers que Angular puede MANDAR
    expose_headers=["X-Total-Count", "X-Request-Id"],                 # headers que Angular puede LEER
)
Regla prácticaSi el mismo header se repite en varios servicios (token, idioma, request-id), no lo pongas en cada llamada: va en un interceptor.
¿Token en un header o en una cookie?

Header Authorization: Bearer: simple, ideal para APIs y apps móviles. El token vive en JavaScript (localStorage o memoria), así que un ataque XSS podría leerlo.

Cookie HttpOnly: JavaScript no puede leerla, el navegador la manda sola. En Angular necesitas withCredentials: true y en Flask CORS(..., supports_credentials=True) con un origen concreto (no *). Hay que protegerse de CSRF.

Para aprender y para APIs propias, Bearer está bien. Esta guía usa Bearer.

Interceptors: código que corre en cada petición#

Un interceptor es una función por la que pasa toda petición de HttpClient antes de salir, y toda respuesta antes de volver a tu servicio. Es el lugar para lo que se repite: poner el token, mostrar un spinner global, manejar el 401, reintentar.

0. La pieza común: un servicio de sesión

Interceptors y guards necesitan saber si hay sesión. Lo guardamos en signals, igual que el estado del buscador:

// core/api.ts
export const API_URL = 'http://127.0.0.1:5000';

// core/auth.service.ts
import { HttpClient } from '@angular/common/http';
import { Injectable, computed, inject, signal } from '@angular/core';
import { tap } from 'rxjs';
import { API_URL } from './api';

export interface Usuario { id: number; nombre: string; roles: string[]; }

@Injectable({ providedIn: 'root' })
export class AuthService {
  private readonly http = inject(HttpClient);

  readonly token = signal<string | null>(localStorage.getItem('token'));
  readonly usuario = signal<Usuario | null>(null);
  readonly logueado = computed(() => this.token() !== null);

  login(email: string, clave: string) {
    return this.http
      .post<{ token: string; usuario: Usuario }>(`${API_URL}/auth/login`, { email, clave })
      .pipe(
        tap((r) => {
          localStorage.setItem('token', r.token);
          this.token.set(r.token);
          this.usuario.set(r.usuario);
        }),
      );
  }

  cerrarSesion() {
    localStorage.removeItem('token');
    this.token.set(null);
    this.usuario.set(null);
  }
}

1. authInterceptor: poner el token

// core/auth.interceptor.ts
import { HttpInterceptorFn } from '@angular/common/http';
import { inject } from '@angular/core';
import { API_URL } from './api';
import { AuthService } from './auth.service';

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).token();
  const esMiApi = req.url.startsWith(API_URL);

  if (!token || !esMiApi) return next(req);            // sin token o API ajena: pasa tal cual

  const conToken = req.clone({ setHeaders: { Authorization: `Bearer ${token}` } });
  return next(conToken);                                // la petición es inmutable: se clona
};
  • next(req) pasa la petición al siguiente interceptor (o al servidor si es el último). Devuelve un Observable con la respuesta.
  • esMiApi evita mandarle tu token a Open Library o a cualquier API de terceros.
  • inject() funciona dentro del interceptor porque Angular lo ejecuta en un contexto de inyección.

// core/error.interceptor.ts
import { HttpErrorResponse, HttpInterceptorFn } from '@angular/common/http';
import { inject } from '@angular/core';
import { Router } from '@angular/router';
import { catchError, retry, throwError, timer } from 'rxjs';
import { AuthService } from './auth.service';

export const errorInterceptor: HttpInterceptorFn = (req, next) => {
  const router = inject(Router);
  const auth = inject(AuthService);

  return next(req).pipe(
    // Reintenta 2 veces solo los GET y solo si es falla de red (0) o del servidor (5xx)
    retry({
      count: req.method === 'GET' ? 2 : 0,
      delay: (err: HttpErrorResponse) =>
        err.status === 0 || err.status >= 500 ? timer(500) : throwError(() => err),
    }),
    catchError((err: HttpErrorResponse) => {
      if (err.status === 401) {                           // token vencido o inválido
        auth.cerrarSesion();
        router.navigate(['/login'], { queryParams: { volver: router.url } });
      }
      return throwError(() => err);                       // el componente igual recibe el error
    }),
  );
};
No reintentes un POSTSi el servidor guardó el préstamo pero la respuesta se perdió, reintentar crea un segundo préstamo. Reintenta solo operaciones que se pueden repetir sin efecto (GET, y PUT/DELETE si tu API lo garantiza).

export async function api<T>(ruta: string, opciones: RequestInit = {}): Promise<T> {
  const token = localStorage.getItem('token');
  const res = await fetch(`${API_URL}${ruta}`, {
    ...opciones,
    headers: {
      'Content-Type': 'application/json',
      ...(token ? { Authorization: `Bearer ${token}` } : {}),
      ...(opciones.headers as Record<string, string>),
    },
  });
  if (!res.ok) {
    const cuerpo = await res.json().catch(() => null);
    throw new Error(cuerpo?.error ?? `HTTP ${res.status}`);
  }
  return res.status === 204 ? (undefined as T) : res.json();
}

API REST de biblioteca

Una API JSON para gestionar autores, libros, socios y préstamos, con PostgreSQL. Lo importante no son las tablas, sino cómo se organiza el código para que crezca sin volverse un desorden: rutas, servicios y repositorios separados, errores claros y operaciones atómicas.

Reglas del negocio que implementa

  • Un libro siempre pertenece a un autor que existe; su año no puede ser futuro.
  • No se puede borrar un autor que tiene libros.
  • El email de un socio es único (sin importar mayúsculas).
  • Un libro prestado no se puede volver a prestar hasta que se devuelva.
  • Prestar = crear el préstamo y marcar el libro como no disponible. O pasan las dos cosas, o ninguna.

Una migración es un archivo que describe un cambio en la base de datos (crear tabla, agregar columna). Es como "git para el esquema": todos los entornos aplican los mismos pasos en el mismo orden.

Rutas y blueprints#

Un blueprint agrupa las rutas de un recurso con un prefijo común. Las rutas son delgadas: leen la entrada, validan el formato, llaman al servicio y devuelven JSON con su código.

  • @bp.get(""), @bp.post("")… son atajos de @bp.route(..., methods=[...]).
  • <int:autor_id> convierte el trozo de URL a entero; si no es número, Flask responde 404 solo.
  • Devolver un dict lo convierte en JSON. La tupla (dict, 201) agrega el código.
  • return "", 204: éxito sin contenido (típico de DELETE).

    g.request_id = request.headers.get("X-Request-Id") or str(uuid.uuid4())

@app.after_request
def despues(respuesta):
    ms = (time.perf_counter() - g.inicio) * 1000
    respuesta.headers["X-Request-Id"] = g.request_id                  # el cliente lo puede citar al reportar un error
    respuesta.headers["Server-Timing"] = f"app;dur={ms:.1f}"          # se ve en la pestaña Red del navegador
    return respuesta

Si before_request devuelve algo (una respuesta), Flask no ejecuta la ruta: así se podría bloquear toda la API. Para bloquear solo algunas rutas se usa un decorador.

# app/routes/auth.py
from functools import wraps

from flask import current_app, g, request
from itsdangerous import BadSignature, URLSafeTimedSerializer   # viene instalado con Flask


def _firmador():
    return URLSafeTimedSerializer(current_app.config["SECRET_KEY"], salt="auth")


def crear_token(socio_id: int) -> str:
    return _firmador().dumps({"id": socio_id})


def verificar_token(token: str, max_age: int = 3600):
    try:
        return _firmador().loads(token, max_age=max_age)   # {"id": 7} o excepción
    except BadSignature:                                   # incluye SignatureExpired
        return None


def requiere_token(vista):
    @wraps(vista)                                          # conserva el nombre de la función (Flask lo necesita)
    def envoltura(*args, **kwargs):
        tipo, _, token = request.headers.get("Authorization", "").partition(" ")
        if tipo != "Bearer" or not token:
            return {"error": "Falta el token"}, 401, {"WWW-Authenticate": "Bearer"}
        datos = verificar_token(token)
        if datos is None:
            return {"error": "Token inválido o vencido"}, 401
        g.socio_id = datos["id"]                           # disponible dentro de la ruta
        return vista(*args, **kwargs)
    return envoltura
# app/routes/prestamos.py
@bp.post("")
@requiere_token                       # el decorador de la ruta va ARRIBA, el guard debajo
def prestar():
    datos = leer_json()
    prestamo = prestamos_service.prestar(libro_id=entero(datos, "libro_id"), socio_id=g.socio_id)
    return prestamo.to_dict(), 201

Transacciones y bloqueos#

Una transacción agrupa varios cambios para que se guarden todos juntos o ninguno. Este helper lo hace con un with:

Prestar un libro hace dos cambios: crear el préstamo y marcar el libro como no disponible. Si el servidor se cae entre los dos, sin transacción quedaría un préstamo de un libro "disponible".

¿Qué es bloquear=True?

Genera SELECT … FOR UPDATE en PostgreSQL: bloquea la fila del libro hasta que termine la transacción. Si dos personas intentan prestar el mismo libro a la vez, la segunda espera, y cuando lee el libro ya ve disponible = False y recibe 409.

SQLite no lo soportaLos tests usan SQLite en memoria, donde FOR UPDATE se ignora. La atomicidad sí se prueba (ver test_atomicidad.py); el bloqueo real solo funciona en PostgreSQL.

// libros/biblioteca.service.ts
import { HttpClient, HttpParams } from '@angular/common/http';
import { Injectable, inject } from '@angular/core';
import { Observable, map } from 'rxjs';

export interface LibroApi {
  id: number;
  titulo: string;
  anio: number | null;
  disponible: boolean;
  autor_id: number;
}

@Injectable({ providedIn: 'root' })
export class BibliotecaService {
  private readonly http = inject(HttpClient);
  private readonly api = 'http://127.0.0.1:5000';

  libros(disponible?: boolean): Observable<LibroApi[]> {
    let params = new HttpParams();
    if (disponible !== undefined) params = params.set('disponible', disponible);
    return this.http
      .get<{ items: LibroApi[] }>(`${this.api}/libros`, { params })
      .pipe(map((r) => r.items));
  }

  prestar(libroId: number, socioId: number) {
    return this.http.post(`${this.api}/prestamos`, { libro_id: libroId, socio_id: socioId });
  }
}

Parte 3 · Arquitectura

Cómo organizar un proyecto que crece

"Arquitectura" es cómo partes el código y cómo se hablan las partes. No hay una correcta: cada una cambia orden por complejidad. Aquí van las que más vas a escuchar, con un diagrama, la estructura de carpetas y cuándo conviene cada una.

Primero: son dos preguntas distintas

Mucha confusión viene de mezclar estas dos preguntas. Se combinan: puedes tener un monolito modular donde cada módulo es hexagonal.

¿Cómo se organiza el código por dentro? Capas · Hexagonal · Limpia · Cebolla · MVC Reglas sobre quién puede importar a quién dentro de una aplicación.
¿Cuántas piezas se despliegan? Monolito · Monolito modular · Microservicios · Serverless Cuántos procesos corren, cuántas bases de datos, cómo se comunican por la red.

Arquitectura en capas (N-capas)#

En una frase: el código se apila en niveles; cada nivel solo usa al de abajo. Es la que usa flask-biblioteca.

Ventajas
  • Fácil de entender y de enseñar
  • Separa HTTP, reglas y SQL
  • Sirve para el 80% de las APIs
Desventajas
  • El negocio depende de la BD (está "arriba" de ella)
  • Tiende a servicios gigantes con todo adentro
  • Cambiar de BD toca la capa de negocio

Úsala cuando: empiezas un proyecto, el equipo es chico, las reglas de negocio son pocas o medianas.

Monolito#

En una frase: toda la aplicación es un solo programa que se despliega junto, con una base de datos. Un monolito puede estar bien ordenado (en capas) o ser un "plato de espagueti".

Ventajas
  • Lo más simple de programar, probar y desplegar
  • Una transacción cubre todo
  • Sin latencia de red entre partes
Desventajas
  • Si no hay reglas, todo termina acoplado
  • Se despliega todo aunque cambies una línea
  • Escala como un bloque
El monolito no es maloLa mayoría de productos exitosos empezaron como monolito. El problema no es "ser uno solo", es no tener límites internos. Para eso existe el monolito modular.

Monolito modular#

En una frase: sigue siendo un solo deploy, pero partido en módulos por tema del negocio, y cada módulo solo se deja usar por su puerta pública. Lo mejor de los dos mundos para equipos chicos y medianos.

app/
├── catalogo/
│   ├── __init__.py       ← exporta SOLO lo público: from .api import buscar_libro, marcar_prestado
│   ├── api.py            ← la "puerta" del módulo (funciones o una clase fachada)
│   ├── models.py         ← internos: nadie de afuera los importa
│   ├── repositories.py
│   ├── services.py
│   └── routes.py
├── prestamos/
│   └── services.py       ← from app.catalogo import marcar_prestado   ✅
│                           from app.catalogo.models import Libro      ❌ prohibido
└── socios/
  • Regla de oro: un módulo nunca importa los modelos ni repositorios de otro. Solo su api.py.
  • Cada módulo es dueño de sus tablas. Nada de JOIN entre tablas de distintos módulos.
  • Las reglas se hacen cumplir con herramientas: import-linter en Python, eslint-plugin-boundaries o Nx en Angular.
  • Si un día un módulo necesita escalar solo, ya está listo para salir como microservicio: su api se vuelve HTTP.

Hexagonal (puertos y adaptadores)#

En una frase: el negocio está en el centro y no sabe nada de Flask, ni de Postgres, ni de HTTP. Habla con el mundo a través de puertos (interfaces), y el mundo se conecta con adaptadores (implementaciones) que se pueden cambiar.

Todas las flechas apuntan hacia adentro: el núcleo no importa nada de afuera. Los adaptadores de la derecha implementan un puerto (línea punteada). Esto se llama inversión de dependencias.

app/
├── dominio/              ← Python puro: NO importa flask ni sqlalchemy
│   ├── libro.py          ← entidad con sus reglas
│   └── puertos.py        ← interfaces: RepositorioLibros, Notificador
├── aplicacion/
│   └── prestar_libro.py  ← caso de uso: coordina dominio + puertos
└── adaptadores/
    ├── entrada/http.py   ← blueprint Flask → llama al caso de uso
    └── salida/
        ├── repo_sqlalchemy.py
        ├── notificador_email.py
        └── repo_memoria.py
# dominio/libro.py — la regla vive aquí, no en la ruta ni en el repositorio
from dataclasses import dataclass


class LibroNoDisponible(Exception):
    pass


@dataclass
class Libro:
    id: int
    titulo: str
    disponible: bool = True

    def prestar(self) -> None:
        if not self.disponible:
            raise LibroNoDisponible(self.titulo)
        self.disponible = False

from .libro import Libro


class RepositorioLibros(Protocol):

    def guardar(self, libro: Libro) -> None: ...


class Notificador(Protocol):
    def avisar(self, socio_id: int, mensaje: str) -> None: ...
# aplicacion/prestar_libro.py — el caso de uso recibe los puertos (no los crea)
from app.dominio.libro import Libro
from app.dominio.puertos import Notificador, RepositorioLibros


class PrestarLibro:
    def __init__(self, libros: RepositorioLibros, notificador: Notificador):
        self.libros = libros
        self.notificador = notificador

    def ejecutar(self, libro_id: int, socio_id: int) -> Libro:
        libro = self.libros.obtener(libro_id)
        if libro is None:
            raise LookupError(f"Libro {libro_id} no existe")
        libro.prestar()
        self.libros.guardar(libro)
        self.notificador.avisar(socio_id, f"Prestaste «{libro.titulo}»")
        return libro

    def obtener(self, libro_id):
        return self._libros.get(libro_id)

Servicios (SOA) y microservicios#

En una frase: la aplicación se parte en varios programas que se despliegan por separado y se hablan por la red (HTTP o mensajes). Cada microservicio es dueño de su propia base de datos.

Ventajas
  • Cada equipo despliega su servicio sin esperar a otros
  • Escalas solo lo que lo necesita
  • Si uno cae, los demás pueden seguir
  • Cada servicio puede usar otra tecnología
Desventajas
  • La red falla: timeouts, reintentos, versiones
  • No hay transacción entre servicios (hace falta saga)
  • Depurar exige logs centralizados y trazas (ODD)
  • Infraestructura: Docker, Kubernetes, gateway, colas

SOA vs. microservicios: SOA (años 2000) también parte en servicios, pero más grandes y conectados por un bus central (ESB) con lógica adentro. Los microservicios son más chicos, independientes y con "tuberías tontas": la lógica está en los servicios, no en el bus.

La advertencia clásicaSi no logras un monolito ordenado, con microservicios obtienes un monolito distribuido: el mismo acoplamiento, pero ahora con latencia de red. Empieza modular; separa cuando un módulo tenga una razón concreta (escala, equipo, ritmo de cambios).

Prompts, skills, agentes y metodologías

Los asistentes de terminal (Claude Code, Gemini CLI, Codex) ya no solo responden: leen tu proyecto, editan archivos, corren tests y delegan trabajo. Esta parte explica las piezas con las que se configuran, las metodologías que mejor funcionan con ellos y cómo dejarlos listos en tu máquina.

Las piezas de un agente en la terminal

ConceptoQué es, en una frase

Prompt: cómo pedir bien#

Un prompt es el mensaje que le das al modelo. Hay dos tipos: el system prompt (instrucciones fijas que define la herramienta o tú en la configuración: "eres un asistente de código…") y el prompt de usuario (lo que escribes en cada turno). La calidad de la respuesta depende sobre todo del contexto que das.

Tarea¿Qué quiero?"Agrega login con token Bearer"
Requisitos¿Qué debe cumplir?"El token solo va a API_URL; 401 → /login"
Restricciones¿Qué no hacer?"No instales librerías; sigue el estilo de libros.service.ts"

haz un login

El modelo adivina: qué framework, dónde, con qué librería, cómo se guarda el token. Probablemente inventa una estructura que no es la tuya.

Concreto

Contexto, tarea, requisitos, límites y cómo verificar. El modelo trabaja sobre tu código y sabe cuándo terminó.

Contexto: angular-buscador/ es Angular 22 con componentes standalone y signals.
La API es flask-biblioteca/ (Flask, 3 capas) en http://127.0.0.1:5000.

Tarea: agregar login con token Bearer.

Requisitos:
- AuthService con signal `token`, login() y cerrarSesion() (guardar en localStorage).
- authInterceptor que agregue Authorization SOLO a peticiones a API_URL.
- errorInterceptor: si llega 401, cerrar sesión e ir a /login?volver=<url>.
- authGuard en las rutas de libros.

Restricciones: no instales librerías nuevas. Sigue el estilo de libros.service.ts.

Verificación: tests con HttpTestingController para el interceptor y el guard;
corre `ng test --watch=false` y no termines hasta que pasen.

Antes de escribir código, muéstrame un plan corto y espera mi OK.

Técnicas que funcionan

  • Señala archivos con @ruta/archivo.ts: el agente lo lee en vez de imaginarlo.
  • Pide un plan primero para tareas grandes (o usa el modo plan). Corregir un plan es barato; corregir 400 líneas no.
  • Da un ejemplo del estilo que quieres ("hazlo como autores_service.py"). Un ejemplo vale más que tres párrafos de reglas.
  • Define "terminado": un comando que debe pasar (tests, lint, build). Es la forma de evitar que "parezca" listo.
  • Una tarea por conversación. Cuando cambias de tema, limpia el contexto (/clear).
  • Explica el porqué de una restricción: "no uses localStorage porque esta app corre en SSR" hace que el modelo tome mejores decisiones en casos que no previste.

---
name: endpoint-flask
description: Crea un recurso REST nuevo en flask-biblioteca siguiendo las 3 capas (modelo, migración, repositorio, servicio, ruta y test). Úsalo cuando pidan "agregar un recurso", "nuevo endpoint" o "CRUD" en la API Flask.

# Crear un recurso en flask-biblioteca

1. Modelo en `app/models/<recurso>.py` e impórtalo en `app/models/__init__.py`
   (si no, Alembic no lo ve).
2. Migración: `flask --app wsgi db migrate -m "<recurso>"`. Revisa el archivo antes de `db upgrade`.
3. Repositorio en `app/repositories/`: solo consultas, sin reglas.
4. Servicio en `app/services/<recurso>_service.py`: reglas y transacción.
   Lanza excepciones de `services/excepciones.py`; nunca devuelvas códigos HTTP.
5. Blueprint en `app/routes/<recurso>.py`. Valida formato con `routes/validacion.py`
   y regístralo en `create_app()`.
6. Test en `tests/test_<recurso>.py` usando los fixtures de `conftest.py`
   (copia la forma de `plantilla_test.py`).
7. Corre `pytest -q`. No termines hasta que pase.

## Reglas
- Nombres en español, como el resto del proyecto.
- Errores de negocio → excepción → `errors.py` los traduce (404/409/422).
  • En el proyecto: .claude/skills/ (se comparte por git). Personales para todos tus proyectos: ~/.claude/skills/.
  • La descripción es lo más importante: es lo que el agente lee para decidir si lo usa. Di qué hace y cuándo usarlo, con las palabras que tú usarías al pedirlo.
  • Lo invocas pidiendo la tarea ("agrega un recurso editoriales") o directamente con /endpoint-flask editoriales.

Agentes, subagentes y orquestador#

Un agente es un modelo que trabaja en ciclo: decide qué hacer, usa una herramienta, mira el resultado y vuelve a decidir. Cuando le pides "arregla el test que falla", no responde de memoria: lee el test, lo corre, edita, lo vuelve a correr.

Subagentes y orquestador

Un subagente es otro agente al que el principal le encarga una parte. Trabaja con su propio contexto (no ve toda la conversación) y devuelve solo un resumen. Un orquestador es el agente que parte la tarea, reparte a los subagentes, junta lo que devuelven y decide el siguiente paso.

PatrónCómo funcionaEjemplo
Cadena (pipeline)La salida de un paso es la entrada del siguienteSpec → plan → código → tests
Paralelo (fan-out)Varios subagentes a la vez, se juntan los resultadosRevisar seguridad, rendimiento y estilo al mismo tiempo
Orquestador-trabajadoresUn agente decide sobre la marcha qué delegar"Migra todos los servicios a la nueva API"
Evaluador-optimizadorUno produce, otro critica, se repiteImplementador + revisor hasta que no haya observaciones
RouterClasifica la petición y la manda al especialista¿Es frontend o backend? → subagente correspondiente

Eres un revisor de código exigente. Revisa `git diff` y responde con una lista:

No edites archivos. Si no encuentras nada, dilo; no inventes problemas.
¿Cuándo vale la pena un subagente?Cuando la tarea genera mucho "ruido" (buscar en cientos de archivos, leer logs largos) que no quieres en la conversación principal, o cuando quieres una mirada independiente (un revisor que no vio cómo se escribió el código). Para tareas chicas, un solo agente es más rápido y barato.

La familia "*-Driven Development"#

Todas dicen "deja que X guíe cómo desarrollas". No compiten: cada una responde una pregunta distinta y se combinan.

BDD · Behavior-DrivenEscenarios de comportamiento¿Hace lo que el negocio espera?Dado / Cuando / Entonces

SDD: Spec-Driven Development#

En una frase: antes de pedirle código a la IA, escribes (con su ayuda) una especificación: qué problema resuelves, qué requisitos debe cumplir, cómo se diseña y en qué tareas se parte. La spec es la fuente de verdad; el código se genera y se verifica contra ella.

Por qué importa con IA: el "vibe coding" (pedir y aceptar lo que salga) funciona para prototipos, pero en un proyecto real la IA rellena los huecos con suposiciones. Una spec cierra esos huecos y se puede revisar en 5 minutos, antes de que existan 500 líneas.

Una spec mínima, para una funcionalidad nueva de flask-biblioteca:

# specs/reservas.md

## Problema
Un socio no puede apartar un libro que está prestado; tiene que volver a preguntar.

## Requisitos (formato EARS: CUANDO … EL SISTEMA DEBE …)
- R1. CUANDO un socio reserva un libro prestado, EL SISTEMA DEBE ponerlo al final de la cola de ese libro.
- R2. SI el socio ya tiene 3 reservas activas, EL SISTEMA DEBE rechazar la reserva con 409.
- R3. CUANDO se devuelve un libro con cola, EL SISTEMA DEBE prestárselo al primero de la cola.
- R4. SI el libro está disponible, EL SISTEMA DEBE rechazar la reserva con 422 ("préstalo directamente").

## Fuera de alcance
- Notificaciones por email. Multas.

## Diseño
- Tabla `reservas(id, libro_id, socio_id, creada_en, estado)`; estado: activa | atendida | cancelada.
- POST /reservas · DELETE /reservas/{id} · GET /socios/{id}/reservas

## Tareas
- [ ] T1. Modelo + migración
- [ ] T2. `reservas_service.reservar()` con R1, R2, R4 + tests
- [ ] T3. Atender la cola al devolver (R3) + tests
- [ ] T4. Rutas + tests de API

## Criterios de aceptación
- `pytest -q` en verde. Cada requisito tiene al menos un test con su id en el nombre (`test_r2_...`).

DDD: Domain-Driven Design#

En una frase: el código debe modelar el negocio y usar sus palabras. Lo propuso Eric Evans (2003). Tiene dos mitades: la estratégica (cómo partir un sistema grande en contextos) y la táctica (los bloques para escribir el código: entidades, objetos de valor, agregados…).

Estratégico: contextos delimitados

Una misma palabra significa cosas distintas en distintas partes del negocio. Para el catálogo, un "libro" es título, autor e ISBN. Para préstamos, es un ejemplar físico que está o no en el estante. En vez de un Libro gigante que sirve para todo, cada contexto delimitado tiene su propio modelo.

Táctico: los bloques

BloqueQué esEn la biblioteca
Lenguaje ubicuoLas mismas palabras en las reuniones y en el códigoprestar(), devolver(), Socio (no User, no checkout())
EntidadTiene identidad que dura en el tiempoSocio con id 7, aunque cambie de email
Objeto de valorSe define por su valor, inmutable, se valida al crearseIsbn("978-…"), Periodo(desde, hasta)
AgregadoGrupo de objetos que se guarda junto y protege sus reglasPrestamo: nadie cambia su fecha de vencimiento por fuera
Evento de dominioAlgo que pasó y a otros les importaLibroDevuelto → atender la cola de reservas
RepositorioGuarda y recupera agregados enterosRepositorioPrestamos.obtener(id)
Servicio de dominioRegla que no pertenece a una sola entidadCalcular la multa según membresía y días de atraso
from dataclasses import dataclass
from datetime import date


@dataclass(frozen=True)                      # objeto de valor: inmutable y se valida al nacer
class Isbn:
    valor: str

    def __post_init__(self):
        digitos = self.valor.replace("-", "")
        if len(digitos) not in (10, 13) or not digitos[:-1].isdigit():
            raise ValueError(f"ISBN inválido: {self.valor}")


@dataclass(frozen=True)                      # evento de dominio: un hecho en pasado
class LibroDevuelto:
    libro_id: int
    fecha: date
DDD + IAPon el glosario del dominio en CLAUDE.md / GEMINI.md ("Socio, no Usuario; Préstamo vence a los 14 días; un Socio tiene máximo 3 préstamos"). El agente usará tus palabras y tus reglas en vez de inventar las suyas, y los nombres coherentes hacen que el código sea más fácil de leer para ti y para la IA.

ODD: Observability-Driven Development#

En una frase: antes de escribir una funcionalidad decides cómo vas a saber, en producción, que funciona, e instrumentas el código para eso desde el principio. Los tests te dicen que funciona en tu máquina; la observabilidad te dice qué pasa con usuarios reales.

Ojo con la sigla"ODD" también se usa para Outcome-Driven Development: guiar el trabajo por resultados medibles de negocio ("reducir a la mitad los libros que vuelven tarde") en vez de por lista de funcionalidades. Las dos ideas se complementan: el outcome dice qué medir; la observabilidad lo mide.
PilarQué esEjemplo
LogsRegistro de eventos, mejor en JSON (estructurado){"evento":"prestamo_rechazado","motivo":"ya_prestado","libro_id":3}
MétricasNúmeros en el tiempoPeticiones por minuto, % de errores 5xx, latencia p95
TrazasEl recorrido de una petición por todos los serviciosAngular → gateway → préstamos → Postgres, con tiempos de cada tramo

En flask-biblioteca, un primer paso: un log estructurado por petición, reutilizando el X-Request-Id de Headers en Flask.

# app/__init__.py, dentro de create_app() (después de before_request)
import json
import logging

log = logging.getLogger("biblioteca")

@app.after_request
def registrar(respuesta):
    log.info(json.dumps({
        "request_id": g.request_id,
        "metodo": request.method,
        "ruta": request.path,
        "estado": respuesta.status_code,
        "ms": round((time.perf_counter() - g.inicio) * 1000, 1),
    }))
    return respuesta

Con el request id, cuando un usuario reporta "falló mi préstamo", buscas ese id en los logs y ves exactamente qué pasó. El estándar para métricas y trazas es OpenTelemetry, que funciona con Flask y Angular.

ODD en apps con IASi tu app usa un LLM, la observabilidad incluye guardar trazas de cada llamada (prompt, respuesta, tokens, tiempo) y correr evals: un conjunto de casos de prueba con respuestas esperadas que corres cada vez que cambias el prompt o el modelo. Son los "tests" de la parte que no es determinista.

Flujo de trabajo recomendado#

  1. Explorar sin tocar: "Lee @app/services/prestamos_service.py y explícame cómo se valida un préstamo. No edites nada."
  2. Planear: modo plan (Shift+Tab) o una spec. Corrige el plan antes de que escriba código.
  3. Implementar en pasos chicos con un criterio de terminado ("hasta que pytest -q pase").
  4. Verificar: tests, y para cambios grandes un subagente revisor con contexto limpio.
  5. Commit: lee el diff tú. Eres el responsable del código, lo haya escrito quien lo haya escrito.
Seguridad básica

No pegues contraseñas ni .env en el chat, y bloquea su lectura en los permisos.

Lee los comandos antes de aprobarlos, sobre todo los que borran, hacen push o tocan producción.

Desconfía de instrucciones que aparezcan dentro de archivos, issues o páginas web que el agente lea: pueden ser prompt injection.
